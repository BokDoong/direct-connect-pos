# TO-BE: 직연동 아웃바운드 재설계 — 요구사항과 설계 논의

> AS-IS(`01-as-is-integrated-partner.md`, `02-as-is-outbound-flows.md`)에서 확인한 문제를 해소하는
> 재설계 논의 문서. 결정된 것은 §7 결정 로그에 기록한다.

---

## 1. AS-IS의 문제 — 왜 재설계하는가

### P1. 확장이 단방향이다 — 파트너 추가는 싸고, 기능 추가는 비싸다

AS-IS는 "새 파트너 추가 = row INSERT"에 최적화됐지만, 그 대가로 **새 정책·API 추가가 전면 수술**이 됐다.
실제로 논의되던 매장 코드 검증·메뉴 코드 검증 API를 추가하려면:

1. `partners`에 `supports_xxx` 컬럼 추가 (스키마 마이그레이션)
2. 전 파트너 row에 값 백필
3. `PartnerApiClient`에 메서드 추가
4. 호출 지점마다 게이트 코드 추가
5. path가 파트너별로 다르면 path 컬럼도 추가

즉 변경의 두 축 중 **파트너 축(행 추가)만 싸고, 기능 축(열 추가)은 스키마+코드 동시 수정**이다.
(전형적인 expression problem — AS-IS는 데이터 축을 선택했고, 기능 축의 비용을 치렀다.
TO-BE는 "파트너 추가도 어차피 코드가 필요해진 이상"(버거킹) 기능 축이 싼 쪽으로 축을 옮기는 결정이다.)

### P2. 파트너별 페이로드 확장을 표현할 수단이 없다 (임계점)

버거킹의 "주문 등록에 결제수단 필드 추가" 요구는 boolean/varchar 컬럼으로 표현 불가.
row 파라미터화 모델의 전제("모든 파트너는 같은 코드를 다른 값으로 실행한다")가 깨진 최초의 사례.

### P3. capability 게이트가 산개되어 있고, 누락을 아무도 못 잡는다

`supports_stock` 체크가 재고 조회 6개 지점에, `supports_store_registration`이 활성화 플로우에 흩어져 있다.
새 호출 지점을 추가하며 게이트를 빠뜨려도 컴파일러·테스트가 잡지 못하고 런타임에 드러난다.
특히 매장 등록은 활성화의 hard 의존(등록 실패 = 활성화 실패)이라 게이트 실수가 활성화 오동작으로 직결된다.

### P4. 파트너의 전모가 코드에 없다

"롯데는 어떻게 동작하는가?"에 답하려면 운영 DB row 조회 + 하드코딩 정책(픽업콜 3회, 취소사유 고정)
+ 산개된 게이트 코드를 대조해야 한다. 파트너 하나의 명세가 한곳에 없어서 온보딩·운영 파악 비용이 컸고
— 이 런북 문서가 필요했던 이유 자체가 이 문제의 증거다.

### P5. 계약값 변경이 리뷰·이력 없이 일어난다

미수락 자동취소 시간은 파트너와의 계약값인데, DB UPDATE 한 번으로 리뷰·git 이력 없이 바뀐다.
반대로 값 실수도 검증 없이 반영된다 — cancel path의 `{orderId}` placeholder 누락, `name`↔URL 문자열
비교 같은 **row 값과 코드 사이의 암묵 계약**은 어기는 순간 런타임 장애다. (옵션 코드 오타 `DPST`↔`DSPT`가
전 주문 오과금으로 이어진 사고 계보가 "값 실수는 걸러지지 않는다"의 실례.)

### P6. 파트너별 동작을 테스트할 수 없다

파트너의 동작이 DB 상태의 함수라서 단위 테스트에 DB fixture가 필요하고, "버거킹 같은 신규 파트너"를
테스트 더블로 시뮬레이션하기 어렵다. 파트너별 계약 테스트가 구조적으로 부재했다.

### P7. 설정·시크릿·정책이 한 테이블에 혼재

`partners` 한 row에 라우팅(base_url)·시크릿(auth_key — 평문 TODO)·capability·정책값이 섞여 있어
보안 경계와 변경 관리 정책(누가, 어떤 절차로 바꾸는가)이 항목별로 다를 수 없었다.

> **문제 ↔ 설계 검증**: §5의 각 설계 결정은 P1~P7 중 무엇을 해소하는지로 평가한다.

## 2. 목표 / 비목표

**목표**
- 아웃바운드(당근 → 파트너) 연동 계층 재설계: **파트너 추가 = 구현 코드 1벌 + 환경 설정 1벌**
- 버거킹 시나리오(주문 등록 페이로드에 결제수단 필드 추가)를 **타입 안전하게** 흡수
- capability(재고 조회, 매장 등록)를 boolean 컬럼이 아니라 **컴파일 타임에 검증되는 형태**로 표현
- **하이브리드 원칙**: 행동(페이로드 구성·capability·정책)은 코드로, 환경 데이터(base_url·auth_key)는 yml/시크릿으로

**비목표**
- 인바운드 콜백 재설계 — 당근이 규격 주도권을 가져 파트너별 분기 자체가 없음 (AS-IS §4)
- 타 연동 유형(FOODTECH/HAPPYORDER)의 재설계 — 직연동 내부 구조에 집중
- 무배포 파트너 추가 유지 — 어차피 페이로드가 다르면 코드가 필요하므로, 파트너 추가가 배포를 동반함을 수용

## 3. 요구사항 매트릭스 (직연동 3사)

| | CJ푸드빌 | 롯데GRS | 버거킹 (차기) |
|---|---|---|---|
| 주문 등록 | ✓ | ✓ | ✓ + **결제수단 필드** (당근페이 결제수단 문자열 매핑) |
| 주문 취소 전파 | ✓ | ✓ | ✓ |
| 재고 조회 (Pull) | ✓ | ✗ | ✗ |
| 매장 등록/해지 | ✓ | ✗ (수기 협의) | ✓ |
| 미수락 자동취소 | 600s | 300s | 미정 (기본 600s 가정) |
| 페이로드 | 공통 규격 | 공통 규격 | 공통 규격 + 필드 추가 |

**전 파트너 공통 규격** (변하지 않는 것 — 추상화의 바닥):
- 인증: Bearer(파트너별 auth_key) / 성공·실패 판정: HTTP status만
- 주문번호: 당근 채번 `order_code` 16자 (롯데 varchar(20) 제한 대응)
- HTTP: connect 3s / read 10s, 재시도 4회 지수백오프 (5xx·타임아웃만)
- 취소는 당근발만 전파, best-effort (실패해도 당근 취소 유지)
- 재고 조회 규격: 요청 = 메뉴코드 리스트 / 응답 = (메뉴코드+수량) 리스트

**capability 조합이 3사 3색**이라는 점이 중요하다: CJ(재고O·매장O), 롯데(재고X·매장X), 버거킹(재고X·매장O).
2개 boolean 컬럼의 4조합 중 3개가 실존 — 플래그가 아니라 타입으로 표현할 가치가 충분하다.

## 4. 플로우 분석(02 문서)에서 발견한 추상화 경계(seam)

AS-IS 아웃바운드 플로우를 100% 확인한 결과, 파트너별 "다름"과 "같음"의 실제 경계는 다음 4개 층이다:

| seam | 파트너별로 다른 것 | 전 파트너 공통인 것 | AS-IS 표현 |
|---|---|---|---|
| **S1. 전송** | base_url, API path | Bearer 고정키, 3s/10s, 재시도 4회(전 API 일괄), HTTP status 판정, order_code 멱등(규격서 계약) | partners row (base_url, path 컬럼) + PartnerApiClient 1벌 |
| **S2. 페이로드** | 버거킹: 결제수단 필드 추가 | 공통 규격 DTO (CJ·롯데 100% 동일), 응답 body 미활용 | 표현 수단 없음 — **임계점** |
| **S3. capability** | 재고(CJ만), 매장 등록(CJ·버거킹) | 주문 등록/취소는 전원 필수 | supports_* boolean 2개 → 코드 게이트 산개 (재고 6지점 + 활성화 hard 의존) |
| **S4. 정책값** | 미수락 자동취소 시간 (600/300/600s) | 픽업콜 3회, 취소사유 고정, 주문코드 16자 채번 (하드코딩) | order_delayed_accept_seconds 컬럼 |

플로우에서 추가로 드러난 사실 (설계 제약):
- **주문 등록은 고객 동기 경로** — 등록 완료까지 고객이 대기하고, 최종 실패 시 결제 자동 취소.
  파트너 추상화의 시그니처는 이 동기 계약을 반영해야 한다.
- **재고 조회는 조회(동기)와 DB 반영(비동기)이 분리** — 파트너 계층의 책임은 조회까지이고,
  저장·노출·수량 검증은 호출자(도메인) 소관. 파트너 인터페이스가 "수량 리스트 반환"에서 끝나야 하는 근거.
- **매장 등록은 활성화 플로우의 hard 의존** — capability 유무가 단순 skip이 아니라 **활성화 플로우의
  분기**를 만든다 (CJ: 등록 실패 = 활성화 실패 / 롯데: 게이트 없이 즉시 활성화).
- 재시도 4회는 HTTP 레이어가 아니라 **파트너 호출 클라이언트 컴포넌트에 @Retryable로** 일괄 적용 → Q4 (해소: TO-BE도 공통 전송 부품에 동일 유지).

## 5. 설계 결정 포인트

### D1. 파트너 추상화의 형태 — 무엇을 인터페이스로 자를 것인가

AS-IS는 "공통 구현 1벌 + DB row로 파라미터화"였다. TO-BE 후보:

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 파트너 전략** | `PartnerClient` 인터페이스, 파트너별 구현 클래스 (CjClient, LotteClient, BurgerKingClient) | 파트너의 모든 "다름"이 한 클래스에 응집. 새 파트너 = 클래스 1개 | CJ·롯데처럼 100% 동일한 파트너는 코드 중복 위험 → 공통 베이스 필요 |
| **B. 공통 구현 + 코드 설정 객체** | 구현은 1벌 유지, DB row를 Kotlin 객체(`PartnerSpec`)로 승격 | AS-IS와 이질감 최소, 중복 없음 | 버거킹 페이로드 확장을 여전히 못 담음 — spec 객체에 람다/전략을 넣기 시작하면 결국 A로 수렴 |
| **C. A+B 절충 (템플릿)** | 공통 규격을 베이스 클래스/조합으로 제공, 파트너 구현체는 **다른 것만** 오버라이드 | 공통 규격이 강한 현실(3사 거의 동일)에 부합. 롯데 구현체는 사실상 선언만 | 베이스가 비대해지지 않게 커스터마이징 포인트 설계 필요 |

**추천: C.** 근거 — 이 도메인의 실제 분포가 "95% 공통 + 5% 파트너 고유"이므로, 순수 전략(A)은 중복을,
순수 설정(B)은 확장 불가를 낳는다. 공통 규격은 당근이 주도하는 계약이므로 베이스에 두는 것이 도메인 사실과 일치한다.

### D2. capability 표현 — supports_stock 컬럼의 후계자

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 인터페이스 분리** | `StockQueryable`, `StoreRegistrable`을 별도 인터페이스로, 지원 파트너만 구현. 사용처는 `is` 검사 | 선언=구현이 한곳에 결합. 미지원 파트너에 해당 메서드 자체가 없음 (호출 불가능을 타입이 보장) | 사용처에 `is` 검사 필요 |
| B. nullable 컴포넌트 | `val stockClient: StockClient?` | 단순 | null 체크가 `is` 검사와 등가인데 선언이 구현과 분리됨 |
| C. supports() 메서드 | `fun supportsStock(): Boolean` + 미지원 시 예외 | AS-IS와 유사 | 런타임까지 실수를 못 잡음 — 재설계 의미 퇴색 |

**추천: A.** "지원 여부"와 "구현"이 한 파일에서 함께 움직이고, 게이트 누락(AS-IS에서 6곳에 산개하던
`supports_stock` 체크를 빠뜨리는 실수)이 컴파일 에러가 된다.

### D3. 페이로드 확장 방식 — 버거킹 결제수단을 어디에 담나

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. DTO 상속 | `BurgerKingOrderPayload : CommonOrderPayload` + 필드 추가 | 직관적 | 직렬화·상속 결합이 취약, 공통 DTO 변경이 전 파트너에 전파 |
| B. 공통 DTO + 확장 map | `extraFields: Map<String, Any>` | 코드 변경 최소 | 타입 안전성 포기 — "DB 컬럼을 map으로 옮긴 것"에 불과, 재설계 취지 상실 |
| **C. 파트너 소유 페이로드 조립** | 도메인 모델(주문) → 파트너 DTO 변환을 파트너 구현체가 소유. 공통 규격 조립기는 재사용 가능한 부품으로 제공 | 파트너별 스키마 자유도 100%, 공통 부품 재사용, 타입 안전 | 파트너마다 DTO 선언 필요 (동일 파트너는 공통 DTO 재사용으로 완화) |

**추천: C.** 버거킹 구현 = 공통 조립기 호출 + 결제수단 필드 한 줄. CJ·롯데는 공통 DTO를 그대로 쓴다.
"페이로드는 파트너와의 계약"이므로 소유권을 파트너 구현체에 두는 것이 개념적으로도 맞다.

### D4. 정책값의 위치 — order_delayed_accept_seconds의 후계자

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 코드 (구현체 선언)** | `override val policy = PartnerPolicy(unacceptedAutoCancel = 300.seconds)` | 정책은 비즈니스 계약 — 코드 리뷰·이력 관리 대상. 파트너의 모든 것이 한 파일에 | 값 변경에 배포 필요 |
| B. 설정 (yml) | 환경 설정으로 유지 | 무배포 변경 | 계약 변경이 리뷰 없이 일어날 수 있음. "행동은 코드로" 원칙과 충돌 |

**추천: A.** 자동취소 시간은 파트너와의 계약서에 있는 값이라 바뀌는 빈도가 낮고, 바뀌면 리뷰를 거쳐야 하는
성격이다. 반면 base_url·auth_key는 환경(dev/prod)마다 다르므로 설정에 남긴다 — 이 경계가 하이브리드 원칙의 실체.

### D5. 파트너별 API path 차이 — register/cancel_order_api_path 컬럼의 후계자

AS-IS에서 path를 컬럼으로 override했다. TO-BE에서는 **구현체가 자체 path를 코드로 선언** (D1-C의
커스터마이징 포인트 중 하나). base_url만 설정에서 주입. → D1 결정에 종속되므로 별도 논의 불필요 시 자동 확정.

## 6. 열린 질문 → ✅ 전부 해소 (2026-08-11)

- Q1. soft/hard 정책의 위치 → **파트너 계층 밖(호출자 측) 확정**. 파트너와 무관한 구매 단계의 속성.
- Q2. 유령주문 보상·자동취소 스케줄링 → **의사코드/동작하지 않는 fun 수준으로만 표기**.
  구현은 아웃바운드 파트너 계층에 집중.
- Q3. 데모/테스트 전략 → **통합 테스트로 동작 증명**. Mock/인메모리/fake로 파트너 서버를 대체.
- Q4. 재시도 위치 → AS-IS 정정 확인: HTTP 레이어가 아니라 **파트너 호출 클라이언트 컴포넌트에
  @Retryable 4회**였음. TO-BE도 공통 전송 부품(PosApiTransport)에 동일하게 둔다.
